# R1a — DSFinV-K: живая проверка выгрузки

Часть задания R1 из `brainstorm.md` (гипотеза «универсальный коннектор»). Дата: 12.08.2026.
Проверено по **первоисточнику**: официальный пакет BZSt `dsfinv_k_v_2_4.zip` скачан и распакован,
машинная схема `index.xml` разобрана поимённо. Плюс руководство по выгрузке из 14 кассовых систем.

**Вердикт гейта волны B: ПРОЙДЕН.** Выгрузку делает сам владелец за 3–5 кликов, без вендора и без
техника. Содержимое богаче, чем мы закладывали. Но есть четыре инженерных нюанса, которые меняют
дизайн приёма, и один — модель тарификации.

---

## 1. Что реально внутри: 20 таблиц, разобрано по официальной схеме

`index.xml` из пакета BZSt описывает **20 CSV-файлов** с точными именами полей **[F]**.
Ниже — только то, что имеет для нас ценность.

### `lines.csv` (Bonpos) — сердце выгрузки, 21 поле

`ARTIKELTEXT` · `ART_NR` · `GTIN` · **`WARENGR_ID` · `WARENGR`** · `MENGE` · `FAKTOR` · `EINHEIT` ·
`STK_BR` (цена штуки брутто) · **`INHAUS`** · `P_STORNO` · `GV_TYP` · `POS_ZEILE` · `BON_ID` **[F]**

Это построчные продажи: что, сколько, по какой цене, в какой товарной группе. Ровно то, чего нет
ни в одной кассовой аналитике для владельца.

**`INHAUS` — отдельная находка.** Флаг «в зале / с собой» стоит **на каждой позиции**. Это и есть
драйвер 7 % против 19 % в немецком гастро. Наше доменное правило «ставку берём из документа, никогда
не угадываем по категории» здесь выполняется буквально: рядом лежит и ставка, и её причина.

### Остальное, что мы будем использовать **[F]**

| Файл | Что даёт |
|---|---|
| `lines_vat.csv` (Bonpos_USt) | НДС **по каждой позиции**: `UST_SCHLUESSEL`, `POS_BRUTTO`, `POS_NETTO`, `POS_UST` |
| `itemamounts.csv` (Bonpos_Preisfindung) | ценообразование позиции: базовая цена, скидки (`TYP`, `PF_BRUTTO/NETTO/UST`) |
| `subitems.csv` (Bonpos_Zusatzinfo) | **компоненты и модификаторы**: `ZI_ART_NR`, `ZI_NAME`, `ZI_WARENGR`, `ZI_MENGE`, `ZI_EINHEIT`, `ZI_BASISPREIS_*` — то есть состав сетов и добавки |
| `transactions.csv` (Bonkopf) | чек целиком: `BON_TYP`, **`BON_START` / `BON_ENDE`**, `UMS_BRUTTO`, `BEDIENER_ID/NAME`, `TERMINAL_ID` |
| `vat.csv` (Stamm_USt) | справочник `UST_SCHLUESSEL` → `UST_SATZ` |
| `cashregister.csv` (Stamm_Kassen) | **`KASSE_BRAND`, `KASSE_MODELL`, `KASSE_SW_BRAND/VERSION`** |
| `businesscases.csv` (Z_GV_Typ) | дневные итоги по типу операции и ставке НДС |
| `payment.csv`, `datapayment.csv` | способы оплаты (наличные/карта) на уровне дня и чека |
| `location.csv` (Stamm_Orte) | Betriebsstätte — мультилокейшн из коробки |
| `cashpointclosing.csv` | `Z_BUCHUNGSTAG`, `TAXONOMIE_VERSION`, адрес, StNr/USt-IdNr |
| `references.csv` | связи между чеками и внешними документами |

### Что это открывает сверх плана

Мы закладывали в волну B только Wareneinsatz-Quote. По факту одной выгрузкой приезжает:

- **продажи по блюдам** (`ARTIKELTEXT` + `MENGE` + `STK_BR`) → ось «популярность» для Menu Engineering
  появляется **на волне B, а не в волне E**;
- **почасовой профиль** (`BON_START`/`BON_ENDE`) → загрузка по часам и дням недели;
- **разделение зал / с собой** → корректная работа с 7/19 % и, отдельно, экономика доставки
  из собственных данных;
- **компоненты сетов** (`subitems`) → вторая опора для ИИ-черновиков рецептур, помимо скана меню;
- **разрез по сотрудникам** (`BEDIENER`) — осознанно **не трогаем**: это персональные данные,
  DSGVO и производственный совет. Поле игнорируем при импорте, в модель не пишем.

**Продуктовая идея из `cashregister.csv`:** после первой выгрузки мы знаем марку и модель кассы →
в следующем месяце показываем владельцу инструкцию **именно под его кассу**, а не общую. Дёшево,
а трение снимает заметно.

## 2. Кто и как выгружает: путь владельца по 14 системам

Источник — руководство «Leitfaden: DSFinV-K-Export aus gängigen Kassensystemen» (Wolters Kluwer,
Stand: Mai 2025) **[F]**. Общий путь: вход с правами админа/менеджера → *Berichte / Datenexport /
Fiskalisierung* или *TSE/DSFinV-K* → пункт «DSFinV-K-Export» (иногда «Kassenprüfung» или
«Prüfdatensatz») → выбрать период → выгрузить.

| Система | Путь | Результат |
|---|---|---|
| **ready2order** | Admin Interface → Einstellungen → Fiskalisierung & TSE → Exporte | ZIP, скачивание |
| **orderbird** | MY orderbird → Datenexporte → DSFinV-K → период + e-mail | ⚠️ **TAR по e-mail** |
| **Lightspeed K-Series** (ex-Gastrofix) | Back Office → Auswertungen → Steuerprüfung | ZIP |
| **gastronovi** | Back Office → Finanzen → DSFinV-K-Export | ZIP |
| **SumUp Kassensystem Pro** | Back-Office → Berichte / Export | ZIP |
| **Tillhub** | Cloud-Backoffice → Berichte / Datenexport | ZIP |
| **helloCash** | Einstellungen → DSFinV-K & TSE | ZIP |
| **Vectron** | Menü → Kassen-Nachschau / Prüfermodus → цель «USB-Stick» | ZIP на флешке; в myVectron-облаке архив 10 лет |
| **JTL-POS** | Menü → Kassenprüfung / Fiskalexport | ZIP |
| **HS-Soft CashAssist** | Web-Portal → Kasse Global → Export (или на кассе: Menü → DSFinV-K) | ZIP, опционально по e-mail |
| **Kasse Speedy** | Menü → Export → Kassenprüfung DSFinV-K | ZIP |
| **ExpressKasse** | Datei → DSFinV-K-Export | ZIP |
| **Sharp Registrierkassen** | журнал на SD/USB → **отдельный конвертер Sharp на ПК** | ZIP |

ready2order подтверждает и со своей стороны: «Bei einer Kassennachschau kannst Du dank einheitlichen
DSFinV-K-Export **mit wenigen Klicks** jederzeit sämtliche Deiner Aufzeichnungen konform
bereitstellen» **[F]**.

**Ответ на вопрос гейта: да, владелец делает это сам.** Ни в одной из 14 систем не требуется вендор,
техник или платная услуга.

## 3. Четыре инженерных следствия — их надо учесть в волне B

1. **Форматов два, а не один.** Большинство отдаёт **ZIP**, orderbird — **TAR**, и не файлом на
   скачивание, а **письмом**. Приём должен принимать оба архива, и **TAR-вложение обязано ловиться
   почтовым инбоксом** `docs-{tenant}@…`, который у нас и так в MVP. Для orderbird это означает
   нулевое трение: владелец просто указывает наш адрес в поле «e-mail» при выгрузке.
2. **Стационарные кассы отдают файл на USB/SD.** Vectron, ExpressKasse, Sharp — это **десктопный
   сценарий загрузки**, а не телефон. Наш продукт mobile-first; для этого пути нужен нормальный
   веб-аплоад с компьютера. Sharp вдобавок требует запустить конвертер на ПК — самый тяжёлый случай.
3. **Это не документ, это датасет.** У ресторана 2 000–4 000 чеков в месяц → десятки тысяч строк
   в `lines.csv`. Никакого LLM: **строго детерминированный CSV-парсер**, потоковая обработка,
   отдельная ветка пайплайна мимо extraction-стадии. Наш `ExtractionProvider` тут не участвует.
4. **Ритм — ручной, месячный.** Автоматической отправки по расписанию ни одна система не предлагает
   **[?]**. Значит UX волны B: напоминание в дайджесте («выгрузите кассу за июль — 4 клика»),
   инструкция под конкретную марку и терпимость к тому, что месяц может быть пропущен.
   Автоматизация — только там, где есть API (ready2order), и это по-прежнему апгрейд, а не основа.

## 4. Следствие для тарификации — важнее, чем кажется

Наш прайс — **пакеты документов** (80 / 200 / 400 док/мес). Одна DSFinV-K-выгрузка — это **один
загруженный файл, но десятки тысяч строк**. Если счётчик спишет её как «1 документ», всё честно;
если пайплайн начнёт считать чеки документами — клиент с тарифом на 200 документов исчерпает пакет
за одну загрузку.

**Решение в модель заложить сразу:** DSFinV-K — отдельный тип потребления, **не расходует пакет
документов**. Иначе первая же выгрузка выглядит как обман.

## 5. Ограничения и остаточные риски

- Руководство по путям меню — **Stand Mai 2025**, авторы сами пишут, что пути меняются с обновлениями
  **[F]**. Наши инструкции нужно версионировать и проверять хотя бы раз в полгода.
- **Проверено по документации и схеме, а не на живом файле.** Реальной выгрузки от реального
  ресторана у нас ещё нет — остаются вопросы качества данных: насколько осмысленно заполнены
  `WARENGR` и `ARTIKELTEXT` у конкретных заведений (кассу часто настраивают как попало,
  и «Sonstiges 19 %» вместо товарной группы — реальный сценарий) **[?]**.
- Само руководство отмечает: выгрузка **не содержит всех данных**, нужных для регистрации кассы
  (например, дату приобретения) **[F]** — для нас нерелевантно, но показывает, что это не «всё о кассе».
- Маппинг кассовых артикулов на наш каталог остаётся ручной работой на старте — как и для строк
  поставщиков.

**Что осталось сделать (дёшево):** попросить у первого же пилотного заведения одну выгрузку за месяц
и прогнать по ней парсер. Это снимет последний вопрос — качество `WARENGR`/`ARTIKELTEXT` в поле.
